# Отчёт по безопасности и персональным данным (Google Play)

Проверка приложения LifeBalance на уязвимости и потенциальные утечки персональных данных для соответствия требованиям Google Play.

---

## 1. Критические и высокие риски

### 1.1 API-ключи и конфиденциальные идентификаторы в репозитории

**Проблема:** В проекте хранятся реальные ключи и идентификаторы:

- **`app/google-services.json`** — содержит:
  - `api_key`: `API_KEY_REDACTED`
  - `client_id` (Android, Web), `certificate_hash`, `project_id`, `storage_bucket`
- **`app/src/main/res/values/strings.xml`** (и локали) — **`default_web_client_id`**:  
  `927055593016-2acud8n2e8i3dq9iclpfufqq5lh1sr5f.apps.googleusercontent.com`

При публичном репозитории эти значения попадают в историю и могут быть использованы для злоупотреблений (квоты, подделка клиента).

**Рекомендации:**

1. **Ограничить ключи в Google Cloud Console:**
   - [API Key restrictions](https://console.cloud.google.com/apis/credentials): ограничить по имени пакета Android (`com.example.mylife.lifebalance`) и по отпечатку SHA-1 релизного ключа.
   - Для Web Client ID ограничения задаются в OAuth consent screen / OAuth 2.0 Client IDs.

2. **Не коммитить реальный `google-services.json` в публичный репозитори:**
   - Добавить `app/google-services.json` в `.gitignore` и хранить файл только локально / в закрытом хранилище (например, CI secrets).
   - В репозитории оставить только пример: `google-services.json.example` с пустыми или подставными значениями и инструкцией по получению файла из Firebase Console.

3. **Web Client ID:** Оставить в коде только для нужного типа OAuth-клиента и убедиться, что в Google Cloud он привязан к вашему приложению и доменам.

4. **После утечки ключа:** Создать новый ключ в консоли, ограничить его, обновить приложение и по возможности отозвать/удалить старый ключ.

### 1.2 Отсутствие явного исключения БД и чувствительных данных из бэкапа

**Проблема:** В `backup_rules.xml` и `data_extraction_rules.xml` явно перечислены только:

- `sharedpref`: `app_settings_sync.xml`
- `file`: `datastore/app_settings.preferences_pb`, `datastore/lifebalance_settings.preferences_pb`

Локальная БД Room (`life_balance_database`) и EncryptedSharedPreferences с ключом БД (`secure_db_key`) в список не входят. При использовании `fullBackupContent` по умолчанию в бэкап попадает только то, что перечислено в правилах, поэтому текущая конфигурация **не включает** базу и ключи. Риск — при изменении правил или неоднозначности реализации можно случайно начать бэкапить персональные данные.

**Рекомендации:**

1. **Явно исключить из бэкапа всё, что содержит персональные данные:**
   - База Room (каталог `databases/`, файлы `life_balance_database*`).
   - Любые SharedPreferences/файлы, где хранятся токены, email, uid (в т.ч. зашифрованные).

2. В `backup_rules.xml` и `data_extraction_rules.xml` добавить комментарии, что в бэкап **не должны** попадать:
   - база данных приложения;
   - EncryptedSharedPreferences с ключом БД и токенами.

3. Периодически проверять содержимое бэкапа (например, через `adb backup`) и убеждаться, что в нём нет email, uid, текста заметок и т.п.

## 2. Средние риски

### 2.1 Передача пользовательского контента на внешний AI-сервис

**Проблема:** Текст баланса и заметок отправляется на Cloud Run (`https://analyzebalance-gavadwesla-uc.a.run.app/`) без идентификатора пользователя в запросе. Это персональные данные (содержимое заметок может быть чувствительным).

**Рекомендации:**

1. В **Privacy Policy** и в описании в Google Play явно указать:
   - какие данные отправляются на сервер (текст для анализа);
   - цель обработки (AI-анализ);
   - что данные не привязываются к аккаунту на вашей стороне (если так и есть);
   - ссылку на политику конфиденциальности бэкенда/Cloud Run, если он обрабатывает данные.

2. На бэкенде:
   - не логировать тело запросов с пользовательским текстом в продакшене;
   - не хранить сырой текст дольше, чем нужно для ответа;
   - использовать только HTTPS (уже используется).

3. Соблюдать лимиты и согласие (у вас уже есть лимиты и согласие на обработку данных AI в настройках).

---

### 2.2 Firebase / Firestore — персональные данные в облаке

**Проблема:** В Firestore хранятся данные по путям `users/{userId}/...` (сферы, задачи, цели, идеи, аффирмации). Локально в Room хранится сущность `User` с `uid` и `email`. Это персональные данные.

**Рекомендации:**

1. **Firestore Security Rules:** Убедиться, что доступ к `users/{userId}` разрешён только при `request.auth != null && request.auth.uid == userId`. Не открывать коллекции на чтение/запись по `userId` без проверки auth.

2. **Политика конфиденциальности:** Чётко описать, что данные синхронизируются с Firebase/Firestore, в каких целях и на каких условиях.

3. Для соответствия Google Play и GDPR: обеспечить возможность удаления аккаунта и данных (в т.ч. удаление документа пользователя и подколлекций в Firestore при удалении аккаунта).

---

### 2.3 Хранение пароля БД и чувствительных настроек

**Текущее состояние:** Используются EncryptedSharedPreferences и Android Keystore для ключа SQLCipher и настроек (язык, тема). Это соответствует лучшим практикам.

**Рекомендация:** Не добавлять в эти же хранилища токены Firebase, email или пароли в открытом виде. Токены/учётные данные — только через EncryptedSharedPreferences/Keystore с отдельными именами файлов и без бэкапа.

## 3. Низкие риски и уже сделанные меры

### 3.1 Логирование

- В release логи отключены через ProGuard (`-assumenosideeffects class android.util.Log`), что снижает утечку данных через logcat. **Оставить как есть.**

### 3.2 Сеть

- Используется только HTTPS (Retrofit, Firebase). **Оставить как есть.**

### 3.3 Манифест

- `FileProvider` с `android:exported="false"` — корректно.
- `MainActivity` с `android:exported="true"` — допустимо для launcher activity.

### 3.4 Контакты поддержки

- Email/Telegram/WhatsApp для обратной связи берутся из `local.properties` (BuildConfig), а не захардкожены в коде. **Рекомендация:** не коммитить `local.properties` с реальными контактами в публичный репозиторий; использовать placeholder в примере.

## 4. Чек-лист для Google Play (Data safety)

При заполнении раздела «Безопасность данных» в Google Play учтите:

| Данные | Собираются? | Цель | Шаринг с третьими сторонами? |
|--------|-------------|------|------------------------------|
| Email | Да (Firebase Auth, локально User) | Регистрация, вход, сброс пароля | Firebase (Google) |
| Идентификатор пользователя (uid) | Да | Синхронизация, привязка данных | Firebase (Google) |
| Текст заметок/целей/сфер | Да | Синхронизация Firestore, AI-анализ | Firestore; текст для AI — ваш бэкенд/Cloud Run |
| Фото (мечты) | Да (если загружаются) | Синхронизация | Firebase Storage |
| Язык/тема | Да (локально и в бэкапе) | Настройки приложения | Только локально/бэкап устройства |

Укажите в форме:
- сбор email и идентификатора;
- передачу данных в Firebase (Auth, Firestore, Storage);
- передачу текста на ваш сервер для AI-анализа;
- возможность шифрования данных (SQLCipher, EncryptedSharedPreferences) и то, что бэкап ограничен только настройками (без БД и токенов), если это так.

## 5. Краткий список действий

1. **Ограничить API-ключ и OAuth client** в Google Cloud по пакету и SHA-1.
2. **Убрать реальный `google-services.json` из публичного репозитория**, добавить пример и `.gitignore`.
3. **Явно исключить из бэкапа** базу данных и любые префы с токенами/ключами; задокументировать это в правилах бэкапа.
4. **Проверить Firestore Security Rules** (доступ только по `request.auth.uid`).
5. **Обновить Privacy Policy** и описание в Google Play: Firebase, AI-сервис, какие данные куда передаются.
6. **Реализовать удаление аккаунта и данных** (в т.ч. в Firestore) для соответствия политикам магазина и GDPR.
7. **Не коммитить `local.properties`** с реальными контактами; использовать placeholder в примере.

После выполнения этих шагов приложение будет лучше соответствовать требованиям Google Play по безопасности и персональным данным.
